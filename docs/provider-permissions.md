# Provider approval modes

Excalibur (xcb) starts native Claude Code in Auto mode and Codex with
automatic approval review. Each provider runs in a private profile and uses
xcb's workspace tools. Automatic review does not expand the files or commands
those tools can access.

Claude must report `permissionMode: auto` when it starts. Codex must report
`approvalPolicy: on-request` and `approvalsReviewer: auto_review`, with its
read-only provider sandbox intact. A provider that reports a different mode
cannot start work. xcb does not silently switch either provider to manual
approval or unrestricted execution.

Codex's automatic reviewer handles requests that would otherwise need a
person, as described in the [official Auto-review documentation](https://learn.chatgpt.com/docs/sandboxing/auto-review).
Registered host tools are available through the
[shared tool bridge](tools.md). The installed desktop computer-use connector
uses Codex's native MCP connection so its approval requests reach the
automatic reviewer. A request for additional human approval stops automatic
work; xcb does not approve it on the person's behalf. Unregistered native
tools remain unavailable.
Provider account or organization restrictions can make an approval mode
unavailable; xcb cannot grant access the provider has withheld.

## Native execution direction

The [north star](vision.md#native-provider-execution) calls for native file,
shell, and network tools for Claude Code and Codex. On macOS,
`workspace_native_exec` runs commands in the granted worktree through each
provider's native tool protocol. It uses an OS policy that allows DNS and
outbound TCP 443, clears the inherited environment, and supplies a private
command home. Host GitHub credentials require a separate workspace option
and a successful authenticated test. Provider-built-in host shell and web
tools remain disabled; the host bridge does not claim that a provider's
built-in command classifier reviewed its arguments.

A task with `native_execution: true` preserves that requirement through resume
and provider changes. The host must first pass `xcb native qualify`, run
`xcb native verify --provider <provider>` for each provider, and select the
workspace with `xcb native grant`. Verification uses an existing account
lock and a disposable workspace, authorizes one command, and records tool
results rather than trusting the provider's answer. Qualification does not
enable real project access. Native tasks cannot use offline replay or the
legacy Codex host command tool. Linux and Windows refuse native commands.

Native backends must retain each provider's approval controls and verify their
reported mode. A native shell requires fresh filesystem, network, cancellation,
and recovery evidence. Enabling a tool or changing a configuration flag cannot
reuse the broker-only evidence. Devin execution remains retired; older account
and session records remain readable, but cannot acquire new execution grants.

## Provider method coverage

The task build provides `xcb native methods --provider codex` and
`xcb native methods --provider claude`. These commands list integration
status without launching a provider, reading credentials, or submitting a
model prompt. The catalog describes the task adapter, not an unrestricted
provider API or every method in xcb's separate sign-in flows.

The catalog accounts for every method in the checked Codex schema: 167
client requests, one client notification, 11 server requests, and 83 server
notifications. Claude coverage accounts for all 29 methods on the pinned
SDK's `Query` interface. SDK session-file utilities and unexposed wire
controls are outside that Query count. Every listed method has a status:
startup, execution, diagnostic, handled by xcb instead of a provider call,
not implemented, rejected, or ignored with a fixed diagnostic.

The checked inventory is in
[`provider-methods.json`](../crates/xcb-runtime/src/provider-methods.json).
Codex coverage binds to the generated schema digest used by this build;
it does not claim support for an arbitrary newer installed Codex. The
comparison command is:

```sh
python3 qualification/provider-methods.py \
  --codex-schema <generated-schema-directory> \
  --claude-sdk node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts \
  --manifest crates/xcb-runtime/src/provider-methods.json
```

Use the offline schema generated by the checked Codex executable with
`app-server generate-json-schema --experimental --out <directory>`.
The comparison rejects schema or SDK method drift. Required Rust tests check
the catalog and adapter refusals; compatibility tests compare the Query
inventory to the installed pinned SDK. Method accounting is not exhaustive
live acceptance, nor proof that every listed method is enabled.

`xcb native describe --account <id>` supports either a Claude or Codex
account and inspects only that account. It submits no model prompt, starts
no coding turn, and grants no workspace access. Inspection records account
and usage metadata through the normal account lock and process cleanup.
Its output separates build-level native qualification from account-specific
live acceptance: metadata inspection establishes neither usable quota nor
native command acceptance for that account.

## Codex integration methods

Codex inspection returns the checked executable identity, available
model/effort choices, optional email and plan, and measured quota windows.
It creates no thread and sends no `turn/start`. It never consumes a reset
credit, even when the account is exhausted. The separate existing account
refresh path can consume an available reset credit; that behavior is not
part of `describe`.

| Codex operation | xcb integration |
| --- | --- |
| `initialize`, `initialized`, `account/read`, `config/read`, `model/list` | Startup checks the private profile, fixed configuration, account display fields, paginated models, and disabled remote control. |
| `account/rateLimits/read` | Records measured limits and resets. Unknown quota stays unknown. |
| `account/rateLimitResetCredit/consume` | Existing quota-refresh behavior only, never metadata inspection. |
| `thread/start`, `turn/start` | xcb opens an ephemeral thread with exact model, effort, tools, and approval controls, then submits one owned turn. |
| `turn/interrupt` | One request naming the admitted thread and turn, followed by independent process and effect checks. |
| `item/tool/call` | Must match a registered tool's started item, arguments, call ID, thread, turn, and single reply. |
| Account, usage, item, reasoning, and terminal notifications | Known shapes and identities are checked; replies, tokens, policy outcomes, and tool effects remain separate facts. |
| `mcpServerStatus/list`, native MCP progress and automatic review | Available only for the separately granted connector. Server configuration alone does not prove tools reached its thread. |
| Command, file, and permission approval requests; native MCP elicitation | Denied or declined and surfaced for attention. xcb does not manufacture approval. |
| `thread/resume`, `turn/steer`, `fs/*`, `command/exec` | xcb owns conversation replay, queued guidance, revision-checked workspace tools, and separately granted native commands instead of raw provider calls. |
| Provider fork/revert/compaction, thread/turn settings, queues, goals, and provider history | Separate future contracts; not exposed as task-adapter calls. |
| Config writes/reload, process APIs, plugins/skills, remote control, realtime, arbitrary MCP calls, and account mutations | Not exposed as task-adapter calls. Sign-in remains an explicit host operation. |
| Unrecognized requests and sensitive model/account/item/turn notifications | Refused before host tools can run. Other unknown id-less notifications carry no authority and produce only a fixed diagnostic. |

Tests iterate the checked client methods to ensure unimplemented calls send
no request, all server-request methods to check refusal before execution,
and all notification methods to check their recorded disposition. Existing
positive fixtures cover startup controls, tool replies, streaming, usage,
policy denials, cancellation, and native connector lifecycles. This is
source/protocol evidence, not a claim of live coverage for disabled features.

## Claude integration methods

Claude inspection reads startup and usage metadata without submitting a
model prompt. Its JSON includes the checked provider build, named account,
Auto-compatible model choices, up to 128 command and agent names, and
allowlisted account display fields. Credential source fields, unknown
provider fields, descriptions, and agent prompts are not returned.
Describing an account does not enable commands, agents, tools, or workspace
access.

Add `--runtime-status` to request MCP status and context with
`detail: summary` on that same metadata connection. This does not inspect a
running coding task. The result names its probe run and observation time;
only context counters/percentage and up to 128 server names, states, and
reported sources are returned. Server configurations, URLs, environments,
errors, tool descriptions, memory paths, and detailed context content are
omitted. A reported server source does not authorize that server. Summary
inspection avoids per-category token-count API calls. Foreign replies,
executable requests, malformed fields, EOF, and excess frames are refused;
the process still must exit before xcb releases the account.

`xcb native verify --provider claude --account <id>` pins live acceptance to
that account rather than letting routing pick another. Unlike `describe`,
verification submits a model prompt and needs subscription usage. The
provider process still must stop cleanly and its command effects must be
recorded before any account can be released.

| Claude SDK operation | xcb integration stage |
| --- | --- |
| `initializationResult`, `supportedModels`, `accountInfo` | Startup projection and account-specific model/identity refresh. Haiku and models reporting `supportsAutoMode: false` are excluded from executable catalogs; effective Auto mode is checked again at launch. |
| `supportedCommands`, `supportedAgents` | Bounded names in the startup projection only. Commands and delegated agents remain disabled. |
| `streamInput`, streamed output | Host-owned single-turn input and streamed replies. Arbitrary background input queues are not exposed. |
| `interrupt`, `close` | One cooperative interrupt for an active cancelled turn, followed by the existing bounded process-group stop and independent exit checks. An interrupt reply is not process-exit evidence. |
| `setModel`, session continuation | xcb owns model selection and durable context replay. These are not unchecked mid-turn model changes or provider transcript resume. |
| `mcpServerStatus`, `getContextUsage` | `describe --runtime-status` requests redacted snapshots from its metadata connection only. Context always requests `summary`; active coding-session inspection remains future work. |
| Provider resume/fork, `reinitialize` | Require exact account/process identity, retained scope, context lineage, and configuration revalidation before activation. Not enabled. |
| `reconnectMcpServer`, `toggleMcpServer`, `setMcpServers` | Require host-owned server grants and a fresh effective tool inventory. Arbitrary SDK configuration is not accepted. |
| `setPermissionMode`, `applyFlagSettings`, thinking controls | Require a reviewed host contract; no permission widening or provider-policy overrides. Not exposed as raw controls. |
| `rewindFiles`, `stopTask`, `backgroundTasks`, `seedReadState` | Require explicit target ownership, effect records, and independently verified cleanup. Provider-managed child tasks, read-state seeding, and filesystem rewinds remain unavailable. |
| `readFile`, `updateSettings`, `reloadPlugins`, `reloadSkills`, `reloadOutputStyles`, `setMcpPermissionModeOverride` | Workspace reads stay with xcb's revision-checked tools. File settings, reloads, and per-server policy changes are not exposed; they require host ownership and a fresh effective inventory. |

Startup, metadata diagnostics, and protocol refusal checks are testable
without model inference while an account is at its weekly limit. Later
controls remain separate work, not capabilities enabled by startup success.
Before exposing any session or runtime mutation, xcb must check the account,
run/process target, expected revision, original workspace/server grant, and
context lineage; record intent; recheck effective configuration and tools;
and preserve uncertain effects until independently reconciled. A provider
reply alone cannot satisfy those checks. The deployed runtime and live
provider checks must match the final artifact before operational activation.

## When a provider denies an action

A permission denial stops automatic continuation and provider switching.
Claude reports these decisions through `system/permission_denied` events and
the result's `permission_denials` list. xcb records the stop even if Claude
labels the overall result a success, and shows a fixed notice without copying
the denied command or its arguments into diagnostics. A later empty denial
list does not erase a denial already observed during the turn.

Codex's policy errors, including its automatic review rejection limit, also
stop the task. xcb does not treat a model's refusal text as evidence of an
account usage limit, or retry a denied action through another provider.

Account and model usage limits are different: xcb can
[switch subscriptions](failover.md) after the provider process exits and the
previous turn's changes are accounted for. The configured model preferences,
account locks, attempt limits, and explicit provider choices still apply.

Steps requiring a sign-in, a payment, or a fact only the owner knows remain
requests for the owner. See [automatic continuation](reflexes.md).

## Delegated agents

Provider child agents are disabled. Selecting `ultra` reasoning effort does
not enable them.

The pinned Codex 0.159.0 executable showed two incompatibilities: children
without inherited history lacked xcb's workspace tools, and full-history forks
could not start from the temporary root session because it has no saved
rollout. A separate probe also observed a grandchild beyond the configured
depth limit. The [full-history](../qualification/codex-0.159.0-delegation-all.json)
and [depth](../qualification/codex-0.159.0-delegation-depth.json) reports retain
the observed behavior.

The [Claude observation](../qualification/claude-2.1.285-auto-denial.json)
confirms Auto mode and the denial wire format. Its synthetic endpoint does
not implement the approval classifier's replies, so no child started. It
records the resulting denial messages. xcb rejects events
that identify a child agent.
